# 房间刷新与延迟核查

核查日期：2026-10-23。仅检查代码、现有日志和监控，未修改运行逻辑或云资源。

## 结论

- 当前共享状态依赖轮询；outbox 已写入，通知 worker 和客户端实时订阅尚未接通。
- 打大A：可见页面每 5 秒刷新，包括历史和汇总页；点数：每 4 秒刷新，历史页不定时刷新。隐藏/卸载停止定时器；恢复显示立即刷新。点数网络恢复回调仍可触发一次后台刷新。
- 两个 store 均有正在读取/写入保护，慢请求期间定时 tick 会跳过，不会不断叠加同类读取。
- 房间页 mount 和 didShow 都调用 openRoom，存在首次重复读取入口，需合并或去重。
- api 配置 256MB、超时 20 秒；体验版套餐本身不能证明性能瓶颈。

## 优化边界

- BE：优先给请求和数据库阶段增加不含业务数据的计时；点数每次快照串行读取 15 张牌，并逐条遍历最多 20 条结果及 20 条变更。拆分当前状态与历史分页，减少串行往返；保留一致性和鉴权。
- FE：合并首次房间读取；统一可见性、断网、退避及读取去重规则；历史按需读取。
- 共享同步：完成变更通知后按版本刷新，保留低频兜底，不能直接删除轮询导致其他成员数据停更。
- 资源：取得阶段耗时后再做内存档位对照测试；本次不升级套餐、不部署。
