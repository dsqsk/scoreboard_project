# 后端迁移操作流程

状态：2026-10-28最终213条记录已迁入北京轻量服务器scoreboard_prod_20261028并开放新端；旧云api维护停写，原云数据保留。HTTPS真实微信登录和原房间展示由用户确认通过；未发布微信正式版，200ms及长期运维验收待完成。

## 目标与边界

- 成功响应必须在数据库事务提交后返回。正常网络、已建立会话下认领/更正/热状态查询 P95≤200ms；首次登录、历史查询单独统计。上线前确定目标并发、数据量及测量网络，未实测不宣称达标。
- 小规模采用单机部署，数据库仅本机访问；HTTPS 反向代理、应用、MySQL、定时异机备份。不引入 Redis、集群或强制长连接。
- 复用 shared 契约、计分规则、整数积分单位、稳定 ID、版本校验和幂等语义；HTTP 入口和数据访问层改造。不能仅搬运现有串行 SDK 访问。
- 全站一次受控停写切换，优先降低复杂度。不双写，不自动在两套后端间故障切换。

## 1. 确认资源与上线条件

- 记录 CPU/内存/磁盘/地域、系统版本、到期日；确认可 SSH 登录和服务器时间同步。
- 确认域名、备案/接入条件、DNS、HTTPS 证书及微信 request 合法域名。正式上线不能依赖开发工具关闭域名校验。
- 确认同一小程序 AppID 的服务端登录凭据可用；密钥仅通过受控服务器配置注入，不提交代码或聊天。
- 确定维护窗口、可接受停写时间、备份恢复点及恢复时间；小程序审核发布时间不作为可精确控制的切换时钟。

## 2. 准备服务器

- 使用普通 Linux 系统；若新装，优先 Ubuntu 24.04 LTS。已有数据时不得直接重装。
- 建立部署账户、SSH 密钥和防火墙。公网开放 HTTPS；SSH 限管理来源；证书验证需要时开放 HTTP。MySQL 和应用端口不直接暴露公网。
- 安装受支持 Node.js LTS、MySQL 和 Nginx/Caddy；固定版本，应用配置自动启动和崩溃重启。
- 配置生产/演练独立数据库和最小权限账户；日志轮转、磁盘/内存告警、HTTPS 到期提醒。
- 数据目录持久化；备份加密存至服务器之外，设置保留期。根据恢复点要求配置全量备份及 binlog 归档，实际演练恢复。

## 3. 后端改造与前端并行准备

后端：

- 新增 HTTPS API、健康检查和会话接口；前端 wx.login 取得 code，服务端向微信换取可信身份并签发可过期/撤销的会话。AppSecret/session_key 不返回前端；请求不接受客户端自报 openId 作为身份。
- 使用相同 AppID/openId 与原 stableId 算法，确保原用户、房间成员和流水继续关联；验证停用用户、退出成员等撤权。
- 实现 MySQL 原生连接池与事务；将身份/成员授权和业务修改收敛进必要事务，消除独立重复身份事务。
- 将 15 张牌、当前积分及版本聚合为活动热状态；历史按需分页，保留原 ID、previousId、顺序、分页与已保存命令回执。不要通过逐条远程读取重现旧链路。
- 幂等键唯一约束，保存原 payloadHash 和 result；同请求同结果、不同载荷冲突。授权、CAS、状态、流水、收据及通知待办保持原子性。
- 原始数据先导入 staging，再生成业务表和热状态；不能仅用通用 JSON 文档表视为性能改造完成。
- 头像单独决策：保留云存储须验证权限和服务端访问；迁移则复制对象并建立旧 fileId 到新引用的映射，覆盖用户及活动历史快照。默认头像直接保留。不得直接删除旧存储。

前端：

- 新增 HTTP 适配与静默会话恢复，继续使用现有业务 DTO 和错误语义；服务地址由发布配置控制。
- 保留原 requestId、未知结果待确认、同牌在途锁、防连点和乱序版本防护；重登录/重试不能生成重复记分。
- 热状态与历史分离，省略历史不能清空已加载历史；首期允许受控轮询，不将 WebSocket 作为迁移前提。
- 准备维护中/需升级提示和真机体验版；检查头像显示、上传、最近房间、分享入口和重新进入。

## 4. 盘点与导出演练

当前模型共 17 个集合：

`users`、`rooms`、`room_members`、`room_codes`、`activities`、`activity_scores`、`activity_cards`、`commands`、`user_room_signals`、`notification_outbox`、`result_slots`、`rate_limits`、`point_changes`、`point_results`、`point_totals`、`da_a_entries`、`da_a_totals`。

- 全部归档；signal/outbox/rate_limits 的导入、丢弃或重建规则逐项确定，不能盲目重放旧通知，也不能让限流重置意外放开风险操作。
- 使用管理端分页完整导出，稳定排序、断点续传；记录环境、集合、数量、文件校验和、导出版本。敏感数据不写入仓库或普通日志。
- 演练可以使用在线导出，但不将跨集合在线导出视为一致快照；正式最终导出在停写且在途请求排空后执行。
- 导入隔离演练库，保留所有业务 ID、时间、revision、积分单位、规则版本、冻结参与者、历史链及命令收据。
- 核对逐集合数量及规范化内容摘要；验证所有房间成员/活动/流水引用、15 牌完整性、归属积分、历史头与链完整性、结算累计。累计规则按对应玩法校验，不擅自重算旧规则数据。
- 重复运行导入应无重复；异常记录阻止切换，不静默跳过。记录实际导出/导入耗时，据此确定维护窗口。

## 5. 验收门槛

- 全库格式/lint/typecheck、对应后端/前端测试和发布构建通过。
- 覆盖建房、加退房、最近房间、点数认领/更正/结算、打大A记分、历史、头像；未实现玩法不扩大范围。
- 验证多人同牌竞争、异牌并发、重复请求、超时后重试、断网恢复、乱序响应、未授权访问、服务重启后的记录恢复。
- 请求带同一 traceId，关联客户端完整耗时及服务端/事务计时；不得记录凭据和原始用户数据。
- Wi-Fi/移动网络真机测试，并按约定并发和代表性数据量统计 P50/P95/P99、错误率和资源占用；先测空请求网络预算，再测真实形状事务。P95≤200ms 及数据正确性未通过，不承诺目标上线。
- 异机备份实际恢复到隔离库并核验；可通过性测试应使用测试房间/数据，不制造真实成绩。

## 6. 正式切换顺序

1. 预部署新后端，写入关闭；保留旧 api 版本、配置及数据库备份，旧定时/后台写入入口盘点完成。
2. 新客户端先发布支持 HTTP、维护态和后端选择；未切换前仍走旧数据源。选路由服务端控制，不允许客户端任意选择可写数据源。
3. 到维护窗口，旧端所有业务写入统一关闭（含资料、访问时间、后台任务）；排空在途事务，暂停新端写入，阻止其他管理端写数据。
4. 最终全量导出、导入、生成热状态并核验；预计超时或校验失败则终止切换，恢复旧端，重新安排窗口。
5. 对指定测试账户开放新端检查，测试数据与正式数据隔离；验证成功后选择新端为唯一写入来源，再开放用户操作。
6. 旧云函数保持停写/维护状态，旧客户端必须升级或提示维护，不能继续写旧库。新端失败时也不能自动回写旧库。
7. 监测错误、延迟、积分一致性、磁盘和内存；低负载观察建议 7 天，覆盖实际使用与备份恢复后再评估下线旧资源，避免无期限双份费用。

## 7. 回退规则

- 新端尚未接收真实写入：关闭新端，直接恢复旧端写入，通知客户端恢复旧来源。
- 新端已接收真实写入：先暂停两端写入并备份新库；导出切换后的用户/房间/记分/命令等全部变化，经反向导入工具合并旧库并校验，再恢复旧端。不能只恢复迁移前备份或只切地址。
- 反向导入未实现并演练前，不具备无损回退条件；此时保持维护，修复新端或恢复其最新备份，不切回陈旧旧库。
- 上线前记录切换时间、数据基线和变更集合；跨切换的未知结果按原 requestId 查询/重放，保留幂等收据避免重复计分。
