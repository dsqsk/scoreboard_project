# 技术选型

日期：2026-10-20  
状态：技术栈已确认，具体数据结构与接口待技术设计。

## 已确认的技术栈

| 层次 | 选型 |
| --- | --- |
| 前端 | Taro + React + TypeScript |
| 全局状态 | Zustand；组件临时输入保留React局部状态 |
| 发布平台 | 微信小程序；不开展其他平台适配 |
| 后端 | 微信云开发云函数 |
| 数据库 | 云开发文档数据库 |
| 多人同步 | 数据库实时监听 |

微信小程序前端使用微信云开发接入体系；不混用独立CloudBase环境的另一套认证与SDK接入方案。具体SDK、运行时和Taro版本在项目初始化时核对兼容性并锁定。

## 数据交互约定

1. 房间加入、记分、公共牌归属变更及结果保存等业务写入统一经过云函数。
2. 云函数根据可信调用身份校验房间成员、当前参与者及对应操作权限，不信任前端传入的身份或计算结果。
3. 服务端执行计分校验与计算；前端可复用公式展示预览，但后端保存结果为最终依据。
4. 数据库实时监听用于更新页面，不负责决定并发操作的胜负。
5. 计分记录与对应累计在同一事务中更新，避免部分保存；公共牌竞争使用事务保证同一号码只有一个归属。
6. 同一业务提交携带稳定请求标识，重复点击或网络重试不重复记账；不同用户主动发起的不同操作不自动合并。
7. 每次计分按条保留流水，累计单独维护，不把无限增长的全部历史放入单个房间文档。
8. 页面恢复或监听重连后读取最新数据；不依赖监听接收完整历史，不提供离线多人合并。
9. 读取与监听同样校验成员访问范围，不能因房间码可分享而开放全库读取。具体安全规则与监听数据组织在技术设计时明确。

## 工程组织建议

以下为实施建议，不代表已完成搭建或额外技术栈确认：

- 全局状态采用Zustand，管理身份、房间快照、连接状态及跨页面待确认请求；组件临时输入继续使用React局部状态。不引入Redux。
- 计分公式作为独立TypeScript模块，与界面和云开发SDK解耦。
- 云开发访问集中封装，页面通过业务接口调用，避免数据库代码散落各页。
- 首版不引入Redis、消息队列、自建WebSocket或自运维服务器。
- 重点测试计分公式、权限、事务原子性、公共牌并发、重复提交及断线重连。

## 选择理由与边界

Taro + React符合用户明确的前端偏好，当前只交付微信端。微信云开发承载房间数据与低频多人记分，减少首版部署运维工作。

取舍是依赖微信云开发的平台接口与数据能力；独立计分模块和集中的数据访问封装可减少业务逻辑与平台的耦合，但不承诺后续迁移零成本。

费用、资源配额、环境配置、运行时版本、数据备份及部署流程尚未确定，不承诺永久免费。PRD中的玩法边界和待确认项继续有效，不由技术选型补全。
