# 台球与扑克记分微信小程序｜产品需求文档

版本：需求基线 v0.2  
日期：2026-10-23  
依据：本次需求讨论中的用户确认；后续确认优先于早期建议。

## 1. 需求目的

为本人和朋友在线下打台球、打扑克时提供共享记分工具，减少口算、漏记和各自记录不一致的问题。通过微信分享或房间码进入同一房间，查看共同记录和个人累计成绩。

产品定位为记分板与计分计算器。参与者在线下判断比赛结果，程序负责必要的加减、乘法、汇总、同步与保存。

成功标准：五种玩法均可按本文公式完成记分；其他成员可以看到已保存结果；重新进入房间后记录仍在；九球无需逐局开局和结束；扑克未主动保存的计算不影响累计。

## 2. 范围总览

| 分类 | 玩法 | 人数 | 记录方式 | 统计单位 |
| --- | --- | --- | --- | --- |
| 台球 | 中式九球 | 2或3人 | 各自快捷加减分，持续记分 | 分 |
| 台球 | 杀球 | 3或4人 | 随机分配初始号码球、展示个人牌与其他人剩余数、记录最终结果 | 颗 |
| 台球 | 打分 | 2～3名本场参与者 | 从公共牌区选择已进球号码，累计并计算输赢 | 分 |
| 扑克 | 打大A | 5人 | 计算器：基础计分结果×底分，主动保存 | 分 |
| 扑克 | 打对家 | 4人 | 计算器：抓一个或抓两个×底分，主动保存 | 分 |

不同玩法分别累计，不将杀球颗数与其他分数相加。累计范围为当前房间，不包含跨房间总榜。

### 3.1.1 首页与创建房间流程

- 首页提供“创建房间”“房间码加入”和最近房间入口。
- 创建流程：点击“创建房间” → 选择游戏模式 → 确认创建 → 创建成功后进入对应模式房间。
- 模式分为台球和扑克：台球包含中式九球、杀球、打分；扑克包含打大A、打对家。
- 未选择模式时不能确认创建，不默认替用户选定模式；选择面板的具体形式由UI/UX确定。
- 选择模式不等于已创建房间，取消或返回首页不产生房间及房间码。
- 创建成功后展示所选模式、房间码和分享入口；其他成员加入后看到相同模式。先选择模式不要求朋友已经入房，开始记分前仍须满足对应人数与准备条件。
- 创建失败保留所选模式并允许重试；重复点击或重试同一次创建请求不得产生多个房间。
- 本次调整不改变已确认的房间内玩法切换能力，也不将模式选择强加到加入已有房间的流程。

### 首页最近房间

- 首页仅展示有限数量的最近房间。用户提出最多2或3个，本版采用最多3个作为设计取值；若调整为2个，保持其余规则不变。
- 按本人最近进入时间倒序排列，同一房间只保留一个条目；不足3个按实际数量展示，不填充占位房间。
- 房间卡片支持左滑，露出“删除”操作；点击删除移除本人最近房间条目，不退出或解散房间，不删除成员、计分记录和累计，不影响其他人的最近房间列表。
- 该操作不是销毁房间的入口，不使用“删除房间”文案。用户仍可通过原房间码或分享重新进入，重新进入后该房间恢复为最近条目。
- 删除成功后从其余未删除条目按顺序补足，首页仍最多3个；没有条目时展示最近房间空态。
- 删除需保存本人列表状态，重新打开首页后不因刷新恢复已删除条目；仅主动重新进入房间才重新加入。
- 删除提交中防止重复请求；失败保留卡片并提示重试，不显示虚假的删除成功。

### 3.2 数据正确性边界

- 同一次保存请求因重复点击或重试，不得生成重复记录；不同成员主动录入的相似结果不能无依据自动合并。
- 九球多人分别加减分可能短暂或持续不平衡，只提示差额，不自动修正他人分数。
- 历史记录必须保留当时的参赛者、底分及计算结果，不随后续成员或底分变化重算。
- 网络失败应明确提示；以成功保存的结果更新共享累计。不包含离线多人合并能力。
- 同步延迟目标、保存时延和容量上限尚未约定，本版不虚设量化承诺。

### 3.3 微信身份、默认个人资料与可选编辑

#### 3.3.1 首次识别及展示

- 微信隐式身份识别后由后端自动分配稳定默认昵称与头像，不强制首次填写资料即可继续创建、加入、分享直达房间。身份读取失败需提示重试，不伪造身份或用资料页替代失败状态。
- 默认昵称由固定词库组成“形容词+的+动物”，如“开心的狗”；昵称允许重复，不保证全局唯一。内部userId唯一，权限、计分、本人标记与操作绑定userId，不能靠昵称或颜色识别人。
- 默认头像为公共SVG简笔画小人模板`person-v1`加随机RGB色。各分量64～224，加权亮度110～200；仅保存模板版本与颜色，不上传默认图片。
- 默认资料只生成/补齐一次并持久化，刷新、重开、多端读取保持一致，前端不能每次渲染随机。
- 保留旧用户自选昵称和已上传头像，未完善用户自动补齐缺失默认资料，不重写已有活动参与者姓名或头像历史快照。
- 个人资料入口、资料预览与房间成员使用同一头像组件。已上传头像优先于默认头像；图片加载失败用昵称首字兜底。
- 默认昵称与颜色均不保证唯一；房间重名自动短后缀未实现，也非本轮已完成要求，后续是否增加单列待确认。

#### 3.3.2 可选编辑与微信快捷填写

- 用户可以不编辑或取消编辑，继续使用默认资料。只改昵称可保存并保留当前头像，无需上传图片。
- 昵称trim后1～32字符且非空；编辑不改变内部身份和历史快照。
- “使用微信头像和昵称”为合并入口：先由chooseAvatar取得用户选择的头像，再聚焦nickname输入框，用户选择微信昵称或手填。平台仍需分别确认，不能宣称一键静默读取两项资料。
- 上传支持JPG/JPEG/PNG/WebP，大小不超过2MB；用户资料保存永久cloud fileID，临时文件路径或临时下载URL不可作为永久头像。
- 上传失败保留昵称并提示，不虚构保存成功；保存结果未知须以原请求ID及原载荷确认，不重复上传或换ID重发。
- 更新资料不改写原活动历史，房间成员读取最新资料；默认模板与颜色的可信值由后端管理。

## 4. 中式九球

### 4.1 需求

- 支持两人、三人；提供快捷正负记分。
- 基础分为犯规1、普胜4、小金7、大金10；让杆普胜8、让杆小金14。
- 三人大金赢家一次记+20，另外两人分别给自己记−10。
- 每人直接修改自己的分数，不选择输赢对象、不自动联动其他人的分数。
- 不维护上下家、击球顺序、自由球或让杆状态。让杆只影响用户所选记分值。
- 持续保存计分流水并更新累计，不要求逐局创建、结束或结算。
- 所有参赛者当前输赢分合计不为0时显示差额，不阻止继续记分。

### 4.2 验收

| 编号 | 场景 | 预期 |
| --- | --- | --- |
| N01 | 三人初始0分，A记大金正分 | A一次变为+20，B、C仍为0，提示合计差额+20 |
| N02 | B、C随后各记−10 | 三人成绩为+20、−10、−10，合计为0，差额提示消除或显示0 |
| N03 | 某人记普胜+4或犯规−1 | 仅本人累计发生相应变化 |
| N04 | 某人记让杆普胜+8或小金−14 | 仅按所选分值记账，不要求选择上下家 |
| N05 | 连续记分后退出再进入 | 分数与流水保留，无需先结束本场 |

不包含黄金九、开球黑金、普通黑金、让杆大金、自动判局及赛事三犯处理。两人模式大金及让杆快捷值完整口径待确认，不直接套用三人+20。

## 5. 杀球

### 5.1 需求

- 支持三人或四人；增加随机发牌，确定每位玩家初始号码球。此前“只记录最终结果、不记录初始归属”的范围约定由本条更新。
- 每次发牌使用1—15号各一张，14、15号对应两张Joker；三人每人5张，四人按4、4、4、3分配。四人中谁分3张的确定方式待确认。
- 一次发牌产生全体参赛者共用的同一份分配结果；重新进入应恢复原结果，不自动重新随机。重复提交同一次发牌不得产生多份结果。
- 页面主体展示自己的号码牌，并展示其他参赛者当前剩余数量；不要求在主体区展开其他人的具体号码。
- 发牌后初始剩余数等于个人获牌数。玩家点击自己的号码牌将其标记为已进，对应剩余数减1，并同步到其他成员页面；牌保留已进状态，便于区分。
- 已进牌再次点击或同一次请求重试不得重复扣减；重新进入恢复牌状态与剩余数。该交互仅由玩家手动确认进球，不自动判断进球有效性。
- 已进牌上方显示“撤销”按钮；点击后恢复为未进并将本人剩余数加1，同步其他成员；重复提交不得重复恢复。
- 自己牌组末尾展示有边框的空白牌，中间为“＋”；点击弹窗选择惩罚转入的号码牌。确认后该球转归本人、恢复为未进，原归属者不再持有该球，双方剩余数按未进球状态重新计算。
- 转归作为一次完整变更保存，不允许同一球同时归两人；转入后仍可正常标记已进或撤销进球。程序不判断惩罚是否成立，由玩家在线下确认。
- 输家记录负的剩余球数，赢家获得所有输家剩余球数之和。
- 不自动判定进球、归属转移或白球犯规；随机发牌是分配号码球的辅助功能，不是线上台球游戏。通过本人点击牌标记已进、牌上方撤销按钮及末尾“＋”选牌完成手动维护。
- 不使用“初始只有5颗或4颗”限制最终剩余颗数，因为线下惩罚可能增加个人名下球数。
- 保存结果后更新该房间的杀球累计颗数。

| K08 | 重复点击发牌或请求重试 | 同一次发牌只生成一份有效分配，不覆盖已生效结果 |

| K10 | 再次点击已进3号或重试同一次请求 | 不重复扣减，A仍剩4颗 |
| K11 | 标记进球后退出并重新进入 | 恢复已进牌状态及剩余数，不恢复为初始数量 |
| K12 | A剩4颗，撤销自己3号的已进标记 | 3号恢复未进，A剩5颗，其他成员同步；重复请求不再次增加 |
| K13 | A通过末尾＋选择B尚未进的6号并确认 | 6号归A且未进，A剩余数加1，B剩余数减1；牌无重复归属 |
| K14 | A通过＋选择B已进的6号并确认 | 6号归A并恢复未进，A剩余数加1，B剩余数不变 |
| K15 | 取消选牌或转归保存失败 | 归属与剩余数均不改变；失败可重试 |
| K16 | 两人同时转入同一球 | 仅一个变更成功，另一人收到状态已变化的提示，无重复归属 |

输入采用“赢家+各输家剩余数”或直接录入正负颗数，后续UI/UX再定；无论入口如何，最终应符合上述公式。

## 6. 打分

### 6.1 需求

- 支持2～3名本场参与者。准备名单必须包含本人，成员互不重复且均属于当前房间；少于2人、多于3人、重复成员、非房间成员或缺少本人均不可开始。
- 本场名单开始后固定，个人基准分（本玩法底分）=120÷本场人数：两人60，三人40；不得用房间总成员数代替本场人数。晚加入者不改变当前名单或基准，下场可重新选择2人或3人。
- 屏幕中间展示1—15号公共牌，总分120；两人比分两列、三人三列，初始进球分0。主数字为当前进球分，净分=进球分−本场基准分；准备说明、结果预览、历史卡片使用对应基准。
- 本场参与者点击未归属牌直接归本人，成功后增加球号分值。每牌唯一归属，并发只接受一个有效操作，失败明确反馈。
- 有效房间成员可查看、退回或改归属，非空目标必须在本场名单；晚加入未参赛成员不得认领给本人或保存本场结果。修正一次扣原分、加新分，显示修改人。
- 必须15张均有有效归属、号码完整不重复、分数合计120才允许主动保存完整结果。保存前过程不计累计。
- 完整结果由服务端按固定人数计算，结果与累计一次保存；同请求重试或重复保存同活动不重复累计。前端不可提交可篡改的可信基准或最终分。
- 保存后本场只读，结算后更正仍待P05确认；可再来一次并重新确认名单，不自动清空或覆盖原活动。
- 两人/三人历史可混合保留，每条结果按自己的参与人数和保存时配置展示，不能用当前活动人数重算历史；累计仅汇总已保存净分。

### 6.2 验收

| 编号 | 场景 | 预期 |
| --- | --- | --- |
| S01 | 三人初始0，A认领6、B认领9 | 比分6、9、0；进度2/15，累计不变，6/9显示归属 |
| S02 | 两名参与者同时认领6号 | 只有一次有效归属，合计只增加6分 |
| S03 | 将A的6号改给B | A−6、B+6，显示修改人，累计不变 |
| S04 | 三人进球分60、40、20，完整保存 | 基准40，净分+20、0、−20，一次累计 |
| S05 | 两人进球分75、45，完整保存 | 两列比分、基准60，净分+15、−15 |
| S06 | 名单不足2/超过3/重复/非成员/不含本人 | 前后端拒绝开始，不产生有效活动 |
| S07 | 两人开场后第三人加入房间 | 本场仍为原两人、基准60；新成员不能认领或保存，可按房间成员权限修正到本场成员 |
| S08 | 不足15张、牌号重复遗漏、合计不为120或归属不合法 | 不允许保存完整结果，不更新累计 |
| S09 | 重试保存或用新请求重复保存同活动 | 只保留一份结果，不重复累计 |
| S10 | 保存两人结果后开始三人活动 | 新基准40，旧两人结果仍按60展示与累计，不改写旧活动 |
| S11 | 三人活动后再开始两人活动 | 新基准60，历史两人/三人结果各自正确展示，净分合计均0 |

### 6.3 边界与规则版本

不支持少于2人或超过3人的本场活动；此前四人示例已撤销，不再保留“任意人数/分数精度待确认”的产品承诺。基准只有60、40，无本玩法舍入问题。不判断击球顺序、犯规或进球有效性，不维护线下扑克发放过程。新活动后端规则版本为`point-ball-v2`；旧活动和历史不追溯改写。

实现与验证记录分别见[前端交付](development/POINT-DELIVERY.md)和[后端交付](development/POINT-BACKEND-HANDOFF.md)。两人支持不等于已完成真实微信多人并发验收，验证范围以交付记录为准。

## 7. 扑克共同需求

- 进入对应计分玩法、开始计算前确认底分。讨论中“进入房间后确认”和“进入之前确认”统一为计算前必须确认，具体页面位置后续确定。
- 只做计分计算器，不发牌、不记录出牌过程、不维护隐藏身份、不判定胜负或名次。
- 最终分数=参与者对应的基础计分结果×底分。
- 分值按钮显示折算结果，不另设计算预览；只有主动确认记分才保存本人流水并更新累计。
- 打大A和打对家均由每人单独保存本人加减分流水，不自动修改其他人成绩；此前全体结果一次提交的方案已替代。

底分的取值范围、小数支持、修改权限及适用时段未定；已保存历史必须使用当时底分，不追溯修改。

## 8. 打大A

### 8.1 需求

- 固定五人，页面显示入局玩家及各自累计分，标明本人。
- 创建打大A房间时先选择底分倍数：1、5、10或自定义输入，确认后创建；自定义数值范围与精度仍待确认。
- 每个人只操作自己的加减分，不选择其他记分对象，不自动联动他人分数。
- 主操作区左侧选择“＋ / −”，右侧基础分按钮集合为1、2、3、4、6、8、16、32；此集合来自用户提供规则中的个人得分，不进行身份或名次判定。
- 按钮上的主数字直接显示基础分×底分倍数。本次明A默认不选中，开启后按钮显示基础分×底分倍数×2，避免用户再次心算。
- “明A ×2”为本次选择按钮，其作用仅限本人的本次计分，不自动修改整个房间或他人的状态。
- 底分倍数展示在房间名下；左侧依次＋、−、本次明A×2，右侧显示折算分值。左侧按钮加宽并铺满其分配列，不保留多余内侧留白；精确列宽按最新样式修订，不沿用旧64px为冻结要求。不显示计算预览，主动点击“确认记分”保存本人流水、更新本人累计。
- 明A为本次选择按钮，不是持续开关；保存成功后复位为普通，失败保留本次选择。切换底分或明A只更新未保存的按钮数值，不改历史。
- 记录保存本人、正负、基础分、底分倍数、明A倍率、最终变化值和操作时间，以便核对。
- 用户提供的规则表仅作参考，不由程序根据主A、同伙、名次、牌型或线下行为自动推断分数。

### 8.2 验收

| 编号 | 输入/操作 | 预期 |
| --- | --- | --- |
| A01 | 创建时选底分倍数5、明A关闭 | 页面显示倍数×5，按钮显示5、10、15、20、30、40、80、160 |
| A02 | 选＋、基础6对应的30按钮 | 按钮显示30且被选中，无独立计算预览；确认后本人累计+30，其他人不变 |
| A03 | 倍数5，开启明A | 按钮更新为10、20、30、40、60、80、160、320；基础6对应按钮显示60 |
| A04 | 选−、明A开启、基础6对应的60按钮 | 确认记分−6×5×2=−60，只减少本人累计60 |
| A05 | 仅切换正负、分值或明A，未确认 | 不新增记录，不改变任何人的累计 |
| A06 | 其他成员查看房间 | 可看到已保存的本人变动，不出现五人结果自动联动 |
| A07 | 重复提交同一次确认 | 只产生一条本人计分流水 |

## 9. 打对家

### 9.1 需求

- 固定四人。创建房间前确认底分，预设1、5、10及自定义，房间名下展示底分。
- 每个人只给自己记分：左侧＋/−按钮加宽并铺满分配列，右侧抓一个（1倍）/抓两个（2倍），按钮主数字为底分乘对应倍数。
- 选择后点击确认记分保存本人流水、更新本人累计，不选择赢家，不自动修改其他三人成绩。
- 没有明A，不显示计算预览或最底部倍数规则说明横栏；移除分值下方倍率说明。是否保留不含倍率的“抓一个/抓两个”短标签待P12确认。

## 10. 首版不包含

- 线上台球或扑克游戏、扑克发牌出牌、规则裁判、自动识别进球。杀球随机分配号码牌属于首版范围。
- 旁观者、赛事组织、排行榜、陌生人匹配。
- 支付、资金转账、提现或以分数自动执行任何资金结算。
- 跨房间成绩混算、复杂权限体系、离线多人同步。
- 尚未讨论的其他台球或扑克玩法。

上述为本次已讨论范围之外的功能，不意味着未来不能扩展。

## 12. 技术与设计约束

交付形态为微信小程序，房间共享数据需要后端持久化及成员间同步。CloudBase云开发是前期建议，尚未形成必须采用的技术决策；部署方式、成本、数据模型在技术设计阶段确定。

本PRD定义行为与验收结果，不固定页面布局、按钮位置和导航。UI/UX阶段应优先减少记分步骤，尤其避免九球逐局操作；不得为了统一页面流程而引入用户明确不需要的规则记录。
